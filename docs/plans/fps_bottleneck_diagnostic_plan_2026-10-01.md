# SMASH FCS FPS 병목 진단 및 개선 계획서

- 작성일: 2026-10-01
- 대상: `D:\Aiming` 기반 Gazebo/ROS 2 시뮬레이션 및 Jetson 배포 파이프라인
- 우선 목표: 현재 5.8~7.1 FPS로 제한되는 시뮬레이션 영상 경로의 병목을 구간별로 분리하고, 실제 UAV 대응 성능과 무관한 시뮬레이터 병목을 알고리즘 병목으로 오판하지 않는다.
- 최종 목표: 20/30/45 FPS 입력에서 추적·조준·수동 격발 성능을 각각 검증하고, 실제 배포에 필요한 최적화 대상을 확정한다.

## 1. 현재 상태 요약

### 1.1 확인된 성능

| 항목 | 현재 측정값 | 해석 |
|---|---:|---|
| Gazebo 카메라/HUD 출력 | 5.8~7.1 FPS | 현재 시스템 전체 관측 FPS를 제한하는 값 |
| 프레임 간격(벽시계) | 중앙값 142.2 ms, P95 248.8 ms | 약 7 FPS 입력에 해당 |
| 촬영→FCS 시작(벽시계) | 중앙값 157.0 ms, P95 302.1 ms | FCS 실행 이전에 큰 지연 존재 |
| FCS 이미지 콜백 | 중앙값 18.1 ms, P95 54.3 ms | 정상 구간에서는 20 FPS 이상 처리 여유 |
| 촬영→조준점(모의 시각) | 중앙값 33.8 ms, P95 41.3 ms | 알고리즘 지연은 화면 FPS보다 작음 |
| LK 추적 | 평균 약 3.0 ms | 현재 병목 아님 |
| HUD 렌더링 | 평균 약 8.4 ms | 고 FPS 입력에서는 2차 병목 후보 |
| YOLO 호출 | 약 100~170 ms, 비동기 | 정상 TRACK FPS를 직접 정지시키지 않음 |
| Jetson 최종 파이프라인 | 20 FPS 입력 유지, 최대 55.3 FPS | TensorRT FP16 384×640 조건 |

### 1.2 현재 결론

현재 6 FPS 전후의 값은 YOLO 단독 처리량이 아니다. 가장 유력한 병목은 다음 경로다.

```text
Gazebo 카메라 센서 생성
  → WSL 소프트웨어 렌더링
  → ros_gz_bridge
  → DDS 이미지 전달
  → FCS 수신
  → 조준/추적/HUD
  → annotated 이미지 및 MJPEG 뷰어
```

CUDA 추론과 WSL D3D12 Gazebo 렌더링을 함께 사용했을 때 `/clock` 정지가 발생해 현재 Gazebo를 소프트웨어 렌더링으로 실행한다. 이 안정성 우회가 카메라 생성률 저하의 1순위 후보다.

## 2. 문제 정의

### 문제 A — 시뮬레이터 입력 FPS가 낮다

- FCS가 처리하기 전에 카메라 프레임 자체가 약 6~7 FPS로만 도착한다.
- 이 조건에서는 FCS 처리 한계와 실제 카메라 운용 성능을 평가할 수 없다.
- 3 km/h 표적에서는 동작하지만 고속·급기동 UAV 성능을 대표하지 못한다.

### 문제 B — 구간별 지연의 책임 범위가 완전히 분리되지 않았다

- 현재 계측은 촬영 시각, FCS 진입, 조준점, HUD, 격발 시각을 제공한다.
- 그러나 Gazebo 센서 렌더 완료, bridge 수신/송신, DDS 수신 시각은 세분화되지 않았다.
- 따라서 소프트웨어 렌더링과 ROS 전송 중 어느 쪽의 비중이 큰지 아직 확정할 수 없다.

### 문제 C — 시뮬레이션과 Jetson 배포 조건이 다르다

- 시뮬레이션: GTX 1050 Ti, PyTorch `.pt`, SEARCH 최대 960, TRACK ROI 640, Gazebo 동시 실행.
- Jetson: Orin, TensorRT FP16 `.engine`, 384×640, 비동기 YOLO+LK.
- 시뮬레이션 FPS를 Jetson 탐지·추적 성능으로 해석하면 안 된다.

### 문제 D — 실제 남은 조준 취약점은 방향 전환 구간이다

- 영상 기반 수동 격발 전체 명중률: 91.46%.
- 왕복 전환점 부근 명중률: 72.9%.
- 그 외 등속 구간 명중률: 96.0%.
- FPS 병목을 해결한 뒤에는 전환 직후 feedforward/속도 추정 안정화 시간을 다시 측정해야 한다.

## 4. 진단 원칙

1. 한 번에 한 구간만 변경한다.
2. 모든 비교는 동일한 표적 궤적, 거리, 화각, 해상도, 시험 길이를 사용한다.
3. 벽시계 FPS와 모의 시각 FPS를 분리해 기록한다.
4. 입력 FPS, 처리 FPS, 출력 FPS를 서로 다른 지표로 기록한다.
5. 평균뿐 아니라 중앙값, P95, 최대값과 0.5초 이상 stall 횟수를 기록한다.
6. 프로파일러 자체 부하는 비프로파일 실행과 비교해 교차 확인한다.
7. 시뮬레이터 결과와 Jetson 결과를 같은 표에 넣되 동일 조건처럼 비교하지 않는다.

## 5. 단계별 실행 계획

### 1단계 — 카메라 생성과 FCS 처리 분리

목적: FCS를 제거해도 Gazebo 카메라가 6~7 FPS인지 확인한다.

시험 조건:

- 640×640, HFOV 0.2 rad, headless.
- 표적 정지 및 3 km/h 왕복 각각 60초.
- FCS, HUD, viewer, YOLO를 모두 끈다.
- `/turret_camera/image_raw` 헤더 timestamp와 벽시계 도착시간만 기록한다.

판정:

- raw가 여전히 10 FPS 미만이면 Gazebo 렌더링/센서가 P0 병목으로 확정된다.
- raw가 20 FPS 이상이면 FCS 또는 ROS 출력 경로가 주 병목이다.

산출물:

- `results/fps_diag/01_camera_only_*.json`
- raw FPS, 프레임 간격 P50/P95/max, `/clock` stall 표

### 2단계 — 렌더링 백엔드 비교

목적: software GL의 성능 손실과 D3D12+CUDA 정지 조건을 재현 가능하게 분리한다.

비교 조합:

| Case | Gazebo 렌더링 | FCS 장치 | 확인 목적 |
|---|---|---|---|
| A | software | CPU/FCS 없음 | software 카메라 상한 |
| B | D3D12 | CPU/FCS 없음 | 하드웨어 렌더링 상한 |
| C | D3D12 | CPU | 렌더링 단독 안정성 |
| D | D3D12 | CUDA `.pt` | `/clock` 정지 재현 |
| E | software | CUDA `.pt` | 현재 안정 기준선 |

수집 항목:

- camera FPS와 RTF(real-time factor)
- `/clock` 최대 공백과 stall 횟수
- GPU 사용률/메모리, CPU 코어별 사용률
- Gazebo 및 CUDA 오류 로그

분기:

- D만 멈추면 WSL GPU 공유/드라이버 경합으로 분류한다.
- B부터 느리면 Gazebo 센서/장면 설정 문제로 분류한다.
- Windows 또는 별도 PC Gazebo에서 정상이라면 WSL 그래픽 경로 문제로 확정한다.

### 3단계 — ROS bridge/DDS 전달 비용 측정

목적: Gazebo 생성률과 ROS 수신률의 차이를 측정한다.

계측 지점:

1. Gazebo 카메라 토픽 발생률
2. `ros_gz_bridge` ROS publish 시각
3. FCS subscriber callback 진입 시각
4. 이미지 변환 완료 시각

시험 매트릭스:

- 320×320 / 640×640 / 960×960
- raw 구독 1개 / raw+annotated / raw+annotated+viewer
- Fast DDS shared-memory 설정 ON/OFF
- FCS ON/OFF

판정:

- Gazebo 토픽은 빠르고 ROS 수신만 느리면 bridge/DDS가 P1 병목이다.
- 해상도에 거의 선형으로 악화되면 복사·직렬화 대역폭 문제 가능성이 높다.
- 구독자 수에 따라 급격히 악화되면 복수 직렬화 또는 annotated 경로를 분리한다.

### 4단계 — 출력 경로 부하 제거 시험

목적: 제어용 파이프라인과 시연용 HUD를 분리한다.

순서:

1. `publish_annotated=false`
2. MJPEG viewer OFF
3. 녹화 OFF
4. 상태/진단 JSON 최소화
5. raw-only FCS 실행

합격 기준:

- raw-only에서 20 FPS 이상 처리.
- HUD를 켰을 때 처리율 하락 10% 이내.
- viewer/녹화는 제어 콜백을 막지 않고 별도 큐에서 최신 프레임만 사용.

개선 후보:

- HUD/MJPEG 별도 프로세스화
- annotated 이미지 발행률 제한(예: 제어 30 FPS, HUD 10~15 FPS)
- JPEG 인코딩 worker 1개와 queue depth 1 적용
- 화면 표시용 프레임 downscale

### 5단계 — 실제 카메라를 모사한 재생 입력 시험

목적: Gazebo를 제거하고 FCS 자체의 실시간 한계를 확인한다.

입력:

- 동일 녹화 영상을 20/30/45 FPS로 정확히 pacing하여 ROS 이미지로 발행.
- 가능하면 Jetson 카메라와 같은 해상도·포맷을 사용.
- 프레임 드롭 정책은 latest-only, queue depth 1.

합격 기준:

| 입력 | 처리율 목표 | P95 촬영→조준점 | 드롭률 |
|---:|---:|---:|---:|
| 20 FPS | 20 FPS 유지 | 75 ms 이하 | 1% 이하 |
| 30 FPS | 30 FPS 유지 | 60 ms 이하 | 3% 이하 |
| 45 FPS | 성능 한계 확인 | 50 ms 목표 | 수치 기록 |

추가 확인:

- YOLO pending 중 LK가 매 프레임 지속되는지
- stale detector 결과 폐기 횟수
- SEARCH 획득시간과 recovery 시간
- HUD ON/OFF 성능 차이

### 6단계 — Jetson 배포 조건 재검증

목적: 시뮬레이터 개선과 별개로 실제 배포 파이프라인의 성능을 확정한다.

기준 구성:

- Orin
- TensorRT FP16 `.engine`
- 384×640
- SEARCH 5프레임 간격, 2회 확인
- TRACK YOLO 보정 20프레임 간격
- LK+YOLO 비동기

수집 지표:

- end-to-end FPS
- 카메라 캡처→bbox, bbox→조준점, 조준점→HUD 지연
- 전력 모드, 클럭, 온도, thermal throttling
- 20/30/45 FPS 입력별 드롭률
- SEARCH와 TRACK 각각의 처리시간

합격 기준:

- 20 FPS 입력 무손실 처리.
- 30 FPS 입력에서 P95 조준점 지연 75 ms 이하.
- 10분 연속 실행에서 thermal throttling 또는 메모리 증가 없음.
- TRACK 중 YOLO 호출이 LK 프레임 처리를 정지시키지 않음.

### 7단계 — 방향 전환 성능 개선 및 재검증

목적: FPS 병목 제거 후 실제 조준 알고리즘의 잔여 문제를 해결한다.

문제 정의:

- 왕복 끝점에서 표적 속도 부호가 순간적으로 바뀐다.
- 기존 속도 추정과 feedforward가 짧은 시간 이전 방향을 유지한다.
- 전체 명중률은 90%를 넘지만 전환점 부근은 약 73%에 불과하다.

개선 순서:

1. 반전 감지 시 과거 속도 이력을 즉시 축소/재초기화
2. feedforward의 속도 부호 전환 처리 검증
3. 반전 감지부터 추정 안정화까지 READY/격발 보류 시간 측정
4. 단순 보류가 아닌 현재 총구-새 리드점 정렬을 기준으로 재허용
5. 3/10/30 km/h 및 8자 기동에서 회귀시험

합격 기준:

- 전체 수동 격발 명중률 90% 이상.
- 전환점 부근 명중률 90% 이상.
- 등속 구간 명중률 95% 이상 유지.
- READY 표시 후 수동 입력이 거부되는 비율과 이유를 별도 기록.

### 8.1 시험별 분기 보고서 작성 규칙

모든 시험 실행은 성공·실패·중단 여부와 관계없이 해당 실행만을 다루는 분기 보고서 파일을 작성한다. 결과 JSON이나 로그만 생성하고 보고서를 생략해서는 안 된다.

- 저장 위치: `results/fps_diag/reports/<실행 ID>.md`
- 실행 ID 형식: `<단계번호>_<시험명>_<날짜시각>`
- 원본 계측 파일과 로그는 `results/fps_diag/runs/<실행 ID>.*`에 같은 ID로 저장한다.
- 동일 설정 반복시험도 각각 별도 보고서를 작성한다.
- 실행 도중 실패하거나 `/clock`이 멈춘 경우에도 실패 원인, 마지막 유효 시각, 정리 상태를 기록한다.
- 보고서가 작성되고 원본 파일 링크가 유효한지 확인하기 전에는 다음 분기로 진행하지 않는다.
- 여러 반복시험의 종합 판단은 개별 보고서와 별도로 `results/fps_diag/reports/<단계번호>_summary.md`에 작성한다.
- 기존 보고서를 덮어쓰지 않는다. 재시험은 새로운 실행 ID를 사용한다.

각 분기 보고서는 최소한 다음 항목을 포함한다.

1. 시험 목적과 검증할 가설
2. 실행 환경과 정확한 설정값
3. 적용 소스 상태 및 실행 명령
4. 원본 JSON·로그·프로파일 파일 링크
5. 주요 측정값(P50/P95/max, FPS, stall, drop)
6. 예상값 대비 결과와 PASS/FAIL/INVALID 판정
7. 병목 귀속에 대한 근거와 아직 확정할 수 없는 부분
8. 다음 분기 선택 및 선택 근거
9. 실행 종료 후 잔류 프로세스 확인 결과

분기 판정 용어는 다음으로 통일한다.

- `PASS`: 해당 단계의 합격 기준 충족
- `FAIL`: 유효한 시험이지만 합격 기준 미충족
- `INVALID`: 시계 정지, 중복 시뮬레이터, 계측 누락 등으로 결론에 사용할 수 없음
- `BLOCKED`: 외부 장비·드라이버·권한 등 현재 범위 밖 조건 때문에 실행 불가

## 9. 완료 기준

다음 조건을 모두 충족하면 FPS 병목 진단을 완료한 것으로 본다.

1. 현재 6 FPS 병목을 렌더링, bridge/DDS, FCS 중 하나 이상으로 수치화해 귀속한다.
2. Gazebo 없는 입력에서 FCS의 20/30/45 FPS 처리 한계를 확보한다.
3. Jetson TensorRT 결과와 시뮬레이션 결과를 동일 조건처럼 혼용하지 않는다.
4. 20 FPS 이상 입력에서 촬영→조준점 P95와 프레임 드롭률을 제시한다.
5. 방향 전환 구간 명중률을 별도 합격 항목으로 관리한다.

## 10. 첫 실행 권고

첫 작업은 코드 최적화가 아니라 `camera-only` 기준선 측정이다. 이 결과가 10 FPS 미만이면 FCS와 YOLO를 추가 최적화해도 시뮬레이션 화면 FPS는 개선되지 않는다. 반대로 camera-only가 20 FPS 이상이면 바로 bridge/DDS 및 annotated 출력 경로를 우선 조사한다.
