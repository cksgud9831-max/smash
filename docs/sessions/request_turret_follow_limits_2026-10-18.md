# 요청서: 포탑 추종 한도와 정렬 정밀도 (2026-10-18)

작성: Claude 세션(뷰어 작업 중 발견). 대상: `turret_command_node.py` / `smash_fcs/aim_follow.py` 를 담당하는 에이전트.
이 세션은 두 파일을 **읽기만 했고 고치지 않았다.** 아래는 관측과 가설이며, 수정 방향은 담당자가 정한다.

## 1. 증상

사용자 녹화(`recordings/smash_20261018_153542_400061.mp4`, `smash_20261018_155613_937293.mp4`)에서 straight 10 km/h,
35 m, 화각 0.12 rad 일 때 **조준선(카메라)이 거의 돌지 않는다.** 표적은 화면을 프레임당 15~20 px 씩 가로질러 1.5 초 만에 나가고,
FCS 는 `표적 화면 이탈 → SEARCH` 를 반복한다. 뷰어 변경과 무관하다(변경 전 15:00 녹화도 카메라 이동량 0).

## 2. 원인 (계측으로 확인)

시험 조건: 헤드리스, `straight 10 km/h`, 반폭 15 m, 화각 0.12 rad, 35 m, FCS 처리 약 30 Hz(모의 시각), 검출기 갱신 프레임 약 3.4 Hz
(`detector_periodic_interval_frames: 10`).

1. **목표 점프 한도 `aim_max_goal_jump_rad=0.012`** — 검출기 갱신 한 번에 목표를 최대 0.012 rad 만 옮긴다.
   추종 가능 최고 속도 ≈ 0.012 × 3.4 Hz × 35 m ≈ 1.4 m/s ≈ **5 km/h.** 표적 각속도는 2.78/35 = 0.079 rad/s 라 따라갈 수 없다.
   기본값으로 돌린 두 번의 실행에서 갱신 6회 중 5회, 사용자 실행(136 s 모의)에서 335회 중 270회(80 %)가 클립됐다.
2. **잠금 전 포획 범위 `aim_acquire_envelope_rad=0.08`** — `lock=0`(READY 1 s 연속 미달)인 동안 시작 자세에서 ±0.08 rad 밖 목표를
   `_on_aim_track`(turret_command_node.py:263~269)이 거부한다(`env_rej`). 점프 한도를 0.05 로 올리면 팬이 0.067 rad/s 로 따라가다가
   0.069 rad 에서 멈췄다. 표적은 STABLE 1 s 뒤 바로 출발해 잠금이 확정될 틈이 없다. 기본값 실행에서 `lock` 은 한 번도 1 이 되지 않았다.
3. 표적이 시야에 머무는 시간은 약 1.5 s, STABLE 까지 약 1 s 라 한도가 맞지 않으면 추종이 시작되기 전에 나간다.

## 3. 시험 변경 사항 (이 세션이 한 것)

- `smash_scene.launch.py` 에 `aim_acquire_envelope_rad`(기본 0.08) 노출. `wsl_setup_smash_fcs.sh` 에 `SMASH_AIM_ACQUIRE_ENVELOPE`
  (기본 0.08), 기존 `SMASH_AIM_MAX_GOAL_JUMP`(기본 0.012) 문서화.
- `simulation/run_smash_fcs.bat` 은 `AIM_JUMP=0.03`, `AIM_ENVELOPE=0.5` 를 기본으로 전달한다(cmd 에서 `set AIM_JUMP=…` 로 덮어씀).
  setup 스크립트 단독 실행 기본값은 그대로다.

## 4. 조합 시험 결과

기준 지표: `smash_fcs/aim_track` 의 `bbox_cx` 와 화면 중심(320 px)의 차(이탈), `align_err_px ≤ align_tol_px` 비율, 팬 관절각.
표적 경로 끝의 방위각은 atan(15/35) = **0.405 rad.**

1회씩(점프 × 범위):

| 점프 | 범위 | 팬 최대 [rad] | 이탈 중앙값 / p90 [px] | 비고 |
|---|---|---|---|---|
| 0.012 | 0.08 | 0.03~0.07 | (이탈) | 기본값. 따라가지 못함 |
| 0.05 | 0.08 | 0.069 | - | 범위가 막아 멈춤 |
| 0.03 | 0.5 | 0.43 | 75 / 109 | 6 s 동안 0.01→0.43 추종 |
| 0.05 | 0.5 | 0.53 | 84 / 212 | |
| 0.1 | 0.5 | 0.46 | 196 / 263 | 과조향 |
| 0.2 | 0.5 | 0.49 | 105 / 105 | 1.2 s 만에 추적 상실 |
| 0.05 | 0.2 | 0.017 | 140 / 140 | 1.4 s 만에 추적 상실 |

반복 3회(범위 0.5 고정):

| 점프 | 첫 연속 추적 [s] | 팬 최대 [rad] | 이탈 중앙값 [px] | 정렬 허용 안 [%] |
|---|---|---|---|---|
| 0.03 | 6.6 / 6.1 / 3.9 | 0.42 / 0.40 / 0.43 | 121 / 188 / 95 | 2 / 1 / 8 |
| 0.05 | 3.2 / 6.3 / 3.2 | 0.52 / 0.53 / 0.28 | 110 / 68 / 181 | 4 / 21 / 0 |

해석: 포획 범위를 0.5 로 풀면 표적을 시야에 유지하며 따라가지만, **정렬 허용(약 32 px) 안에 드는 비율이 0~21 % 로 낮아
READY·격발 정밀도는 부족하다.** 0.03 은 팬이 경로 끝(0.405 rad)에서 멈춰 과조향이 없고, 0.05 는 끝점을 넘어서(0.52~0.53) 표적을 놓친다.
표적이 끝점에서 되돌아오면 SEARCH 중인 포가 돌아가지 않아 약 10.8 s 주기로 LOST 가 반복된다(재포착 큐 없음).

## 5. 가설 (미검증)

`AimTrackFollower.update` 는 원시 목표가 한도에 걸리면 `self.reset()` 을 부른다(aim_follow.py:280~284, 최종 클립 303~305).
클립 구간에서는 각속도 이력이 매번 지워져 `rate_valid=False` → `GoalRamp`(갱신 사이 연속 이동)가 동작하지 않고, 목표는 갱신마다
0.012 rad 씩 계단으로만 움직인다. 반대로 한도를 키우면 클립이 사라져 피드포워드(0.19 s)가 켜지고 과조향이 나타난다.
2026-09-29 의 "피드포워드가 잠금 순간 발산" 메모와 같은 계열로 보인다. 확인하려면 클립 횟수와 `rate_valid` 가 참인 비율을 한도별로 비교하면 된다.

## 6. 요청

1. 클립을 "목표 포화"로 처리하되 각속도 이력을 지우지 않고, 포화된 구간에서도 연속 이동이 이어지게 할 수 있는지 검토.
2. 잠금 확정 전 포획 범위(0.08 rad)가 이동 표적 시연에서 추종을 막는 문제의 해법. 예: 표적이 STABLE 이 된 뒤에는 범위를 풀거나,
   범위를 표적 이동 방향의 누적각으로 넓히기.
3. SEARCH 로 돌아갈 때 포가 직전 표적 방향(또는 탐색 자세)으로 복귀·재포착하는 동작.
4. 위 조합(점프 0.03, 범위 0.5)은 임시값이다. 목표가 어긋나면 한도를 바꾸지 말고 위 항목으로 정리할 것.

## 7. 재현

```bash
SMASH_AIM_MAX_GOAL_JUMP=0.03 SMASH_AIM_ACQUIRE_ENVELOPE=0.5 \
SMASH_HEADLESS=true SMASH_TARGET_MOTION=straight SMASH_TARGET_SPEED_KMH=10 SMASH_TARGET_HALF_LENGTH=15 \
SMASH_CAMERA_HFOV=0.12 SMASH_ENABLE_FIRE_CONTROL=true \
bash /mnt/d/Aiming/scripts/wsl_setup_smash_fcs.sh run
```

로그: `~/.ros/log/python3_*.log` 의 `[AIMDIAG]` 줄(`raw_clip`, `final_clip`, `env_rej`, `accepted`, `lock`, `goal_pan`).
`aim_track`·`joint_states` 를 구독해 기록한 계측 스크립트는 세션 scratchpad(`aim_trace.py`)에만 있다.
측정 전에 WSL 에서 다른 SMASH 실행이 없는지 먼저 확인할 것(런처 cleanup 이 다른 실행을 죽인다).
