# SMASH 세션 작업 정리 — Gazebo 시뮬레이터 성능 개선 (2026년 9월 12일)

이 문서는 "시뮬레이션 스크립트를 실행하면 너무 오래 걸려 시뮬레이터로 쓸 수 없다"는 문제를
진단하고 수정한 작업을 정리한 것이다. 대상은 D 드라이브 Aiming 폴더의 simulation 및 scripts
디렉터리이며, 모든 수치는 WSL2 Ubuntu 24.04 / GTX 1050 Ti / CPU 4코어 / RAM 15GB 환경에서
직접 실행해 측정한 값이다.

> **이어진 작업(2026-09-12 후속):** 최우선 미해결 항목이던 "포탑이 명령을 따르지 않음"의
> 원인을 규명하고 우회 수정을 적용해 동작을 확인했다. 8절과 9절 사이의 **0절** 참고.
> 이어서 탐지 -> 조준점 -> 격발 통합 검증을 돌린 결과는 **11절**, 거기서 나온 남은 일
> 4건을 처리한 결과는 **12절**, 거기서 다시 남은 일을 처리한 결과는 **13절** 에 있다.
> 사용자가 런처 5번으로 실행하다 발견한 기동 실패는 **14절** 에 있다.

## 1. 문제와 원인

사용자가 사전에 WSL 환경을 점검해 둔 상태였고, 그 결과는 다음과 같았다. 기본 OpenGL 은
llvmpipe(CPU 렌더링)로 동작하지만, `GALLIUM_DRIVER=d3d12` 와 NVIDIA 어댑터를 지정하면
GPU 가속이 정상 동작한다는 것이다.

조사 결과 원인은 WSL 환경이 아니라 실행 스크립트 자체에 있었다. `scripts/wsl_setup_smash_fcs.sh`
의 `run()` 함수가 다음 한 줄로 CPU 렌더링을 강제하고 있었다.

```
export LIBGL_ALWAYS_SOFTWARE=1
```

즉 사용자가 환경을 어떻게 맞춰 두어도, 런처(`run_smash_fcs.bat`)의 4~6번 메뉴로 실행하는 한
Gazebo 는 항상 CPU 로 렌더링되었다. 이 줄은 커밋 `a896dc1`("simulation 패키지 구조화 및
Gazebo ROS2 시뮬레이터 런처 통합")에서 유입되었다.

렌더러별 확인 결과는 다음과 같다. `LIBGL_ALWAYS_SOFTWARE=1` 은 `GALLIUM_DRIVER` 가 함께
지정되면 무시되므로, 두 변수를 동시에 켜도 GPU 로 동작한다.

| 환경변수 조건 | 렌더러 | 가속 |
|---|---|---|
| 기본값 | llvmpipe (LLVM 20.1.2) | 없음 |
| `LIBGL_ALWAYS_SOFTWARE=1` | llvmpipe | 없음 |
| `GALLIUM_DRIVER=d3d12` + NVIDIA 지정 | D3D12 (GTX 1050 Ti) | 있음 |
| EGL surfaceless(헤드리스 경로) + d3d12 | D3D12 (GTX 1050 Ti) | 있음 |

헤드리스 서버가 쓰는 EGL surfaceless 경로에서도 GPU 가 잡히는 것을 확인했으므로, 헤드리스
모드에서도 이 수정이 유효하다. PyTorch 는 별도 문제 없이 CUDA 를 인식한다
(torch 2.14.0+cu126, `cuda True`).

## 2. 수정 내용

### 2.1 렌더러를 GPU 로 전환 (핵심 수정)

`scripts/wsl_setup_smash_fcs.sh` 의 `run()` 에서 CPU 렌더링 강제를 제거하고, Mesa D3D12
드라이버로 NVIDIA GPU 를 지정하도록 바꿨다. GPU 가 없는 PC 를 위해 `SMASH_GL_BACKEND=software`
로 이전 동작으로 되돌릴 수 있게 두었다.

```
SMASH_GL_BACKEND="${SMASH_GL_BACKEND:-d3d12}"
if [ "$SMASH_GL_BACKEND" = "software" ]; then
    export LIBGL_ALWAYS_SOFTWARE=1
else
    unset LIBGL_ALWAYS_SOFTWARE
    export GALLIUM_DRIVER=d3d12
    export MESA_D3D12_DEFAULT_ADAPTER_NAME="${MESA_D3D12_DEFAULT_ADAPTER_NAME:-NVIDIA}"
fi
```

### 2.2 그림자 끄기

사용자 요청에 따라 `ciws_turret/worlds/turret_world.sdf` 의 `<shadows>` 와 태양광
`cast_shadows` 를 모두 `false` 로 바꿨다. 다만 아래 4절에 적은 대로 속도 향상은 측정되지
않았다. 렌더링 부하를 줄이는 것 자체는 무해하므로 끈 상태로 두었을 뿐이다.

### 2.3 문서 갱신

`simulation/environment_setup_guide.md` 4절에 GPU 렌더링 환경변수와 확인 방법
(`glxinfo -B` 결과가 `D3D12 (NVIDIA ...)`, `Accelerated: yes` 여야 함)을 추가했다.

## 3. 측정 결과 (핵심 성과)

모두 헤드리스 모드, 표적 드론 스폰 포함, 동일 절차로 측정했다.

### 3.1 월드만 실행 (FCS 미기동)

| 항목 | CPU 렌더링 | GPU 렌더링 |
|---|---|---|
| 카메라 | 12.2 Hz | 18.0 Hz |
| 레이저(PointCloud) | 18.5 Hz | 28.6 Hz |
| Gazebo 서버 CPU | 200% | 120% |

### 3.2 FCS 포함 전체 파이프라인

| 항목 | CPU 렌더링 | GPU 렌더링 |
|---|---|---|
| 카메라 | 5.6 Hz | 13.1 Hz |
| FCS 처리율(image_annotated) | 3.8 Hz | 10.2 Hz |
| Gazebo 서버 CPU | 200% | 64% |

FCS 처리율 기준 약 2.7배 개선이다. GPU 렌더링 동작은 Ogre 로그의
`GL_RENDERER = D3D12 (NVIDIA GeForce GTX 1050 Ti)` 로 직접 확인했다.

또한 Gazebo 의 실시간 계수(real_time_factor)는 두 경우 모두 약 1.0 으로 동일하게 보고된다.
즉 실시간 계수만 보면 문제가 드러나지 않으며, 실제로 느려지는 지점은 센서 발행 주기다.
앞으로 성능을 판단할 때는 실시간 계수가 아니라 카메라·레이저 토픽 주기를 봐야 한다.

## 4. 시도했으나 효과가 없던 것 (투명성)

측정 편차가 크므로, 아래 두 항목은 "효과 없음"이 아니라 "이 환경에서는 편차보다 작아 확인
불가"로 읽는 것이 정확하다.

### 4.1 그림자 끄기 — 향상 확인되지 않음

그림자를 끈 직후 전체 파이프라인은 오히려 13.1 → 11.9 Hz 로 측정되었다. 이후 그림자
on/off 를 번갈아 반복 측정했으나 동일 조건 사이의 편차가 조건 간 차이보다 커서 결론을 낼 수
없었다. 사용자 요청 사항이므로 끈 상태를 유지한다.

### 4.2 배경(`<sky>`) 제거 — 향상 없어 미적용

sky on/off 를 3회씩 번갈아 측정한 결과는 다음과 같다.

| 회차 | sky 켬 | sky 끔 |
|---|---|---|
| 1 | 16.7 Hz | 12.8 Hz |
| 2 | 19.6 Hz | 11.8 Hz |
| 3 | 8.9 Hz | 12.2 Hz |
| 평균 | 15.0 Hz | 12.3 Hz |

배경을 껐을 때가 오히려 느리거나 같았으므로 적용하지 않았다. sky 켬 조건의 편차
(8.9~19.6 Hz)가 매우 크다는 점도 함께 기록해 둔다.

## 5. 카메라 해상도 실험 (미적용, 결정 필요)

카메라 해상도를 640x640 에서 320x320 으로 낮춰 측정했다. URDF 의 설치본을 직접 수정해
2회 반복 측정했다.

| 회차 | 해상도 | 카메라 | FCS 처리율 |
|---|---|---|---|
| 1 | 640 | 8.8 Hz | 6.5 Hz |
| 1 | 320 | 19.5 Hz | 20.2 Hz |
| 2 | 640 | 10.0 Hz | 7.2 Hz |
| 2 | 320 | 21.4 Hz | 21.0 Hz |
| 평균 | 640 | 9.4 Hz | 6.9 Hz |
| 평균 | 320 | 20.4 Hz | 20.6 Hz |

해상도를 절반으로 낮추면 FCS 처리율이 6.9 → 20.6 Hz 로 약 3배 오른다. 2회 반복에서 모두
같은 방향으로 일관되게 나왔고(640: 6.5/7.2 Hz, 320: 20.2/21.0 Hz), 조건 간 차이가 동일
조건의 편차보다 훨씬 크다. 이번 세션에서 측정한 조건 중 렌더러 전환 다음으로 효과가 크며,
목표치 30 Hz 에 가장 근접시키는 방법이다. 다만 다음 두 가지
부작용을 반드시 함께 고려해야 하며, 그래서 아직 적용하지 않았다.

1. **탐지 정확도 저하.** 35 m 거리의 드론은 640 에서 가로 약 21픽셀이지만 320 에서는 약
   10픽셀이 된다. 본 시스템의 표적이 바로 이 "작고 먼 드론"이므로 영향이 직접적이다.
2. **READY 판정 기준이 두 배로 느슨해짐.** `smash_fcs_node.py` 의 정렬 허용오차
   `_align_tolerance_px` 가 35.0 픽셀 고정값이다. 픽셀 기준이므로 해상도를 절반으로 줄이면
   같은 35픽셀이 두 배의 각도를 의미하게 되어, 격발 준비 판정이 소리 없이 완화된다. 기존에
   기록해 둔 명중률 수치와 직접 비교가 불가능해진다. 해상도를 낮춘다면 이 상수도 함께
   비례 조정해야 한다.

또한 속도 이득의 출처를 정확히 해 둘 필요가 있다. `bridge/optical_flow_tracker.py` 의 YOLO
호출(167행 ROI 경로, 197행 전체 프레임 경로)은 `imgsz` 를 넘기지 않으므로 Ultralytics 기본값
640 으로 레터박스된다. 즉 카메라 해상도를 낮춰도 **YOLO 추론 비용 자체는 줄지 않으며**,
줄어드는 것은 영상 전송(ros_gz_bridge), cv_bridge 변환, HUD 렌더링 비용이다. 추론 비용까지
줄이려면 `predict(..., imgsz=320)` 을 별도로 지정해야 한다.

## 6. 남은 병목과 다음 후보

카메라가 목표치인 30 Hz 에 아직 못 미친다. 남은 병목은 GPU 셰이딩이 아니라 **CPU 4코어
경합**으로 보인다. 근거는 두 가지다.

1. GPU 쪽 장면 단순화(그림자, 배경)가 전부 무반응이었다.
2. 전체 실행 시 Gazebo 약 120%, FCS/YOLO 노드 약 90%, 이미지 브리지 약 27% 로 4코어를
   서로 물고 있다.

다음 후보는 아래 세 가지다.

1. 카메라 해상도 조정 (5절 참고. 정확도 손실과 `_align_tolerance_px` 동반 수정 필요)
2. 카메라·레이저 `update_rate` 를 30 에서 15 로 낮춰 목표 자체를 현실화
3. ~~`.wslconfig` 로 WSL 에 할당된 CPU 코어 수 증설~~ — 확인 결과 불가능하다. 호스트가
   i5-7400 물리 4코어(HT 없음)라 WSL2 가 이미 전부 쓰고 있다. 10절 참고.

2번과 3번의 실측 결과는 10절에 정리했다. 결론만 말하면 2번은 효과가 없어 되돌렸고 3번은
불가능하며, 남은 유효한 수단은 1번뿐이다.

## 8. 측정 방법과 한계

1. 속도 측정은 `ros2 topic hz` 로 했다. 이 명령 자체가 CPU 를 쓰므로 실제 주기는 기록된
   값보다 다소 높을 수 있다.
2. 동일 조건 반복 측정에서도 편차가 크다(예: 같은 조건에서 8.9 Hz 와 19.6 Hz). 4코어 환경의
   스케줄링 경합 때문으로 보인다. 따라서 2배 미만의 차이는 유의미하다고 판단하지 않았다.
3. 이번 측정은 모두 헤드리스 모드 기준이다. Gazebo 3D GUI 창을 띄우는 모드는 측정하지
   않았다.
4. 격발 제어(`enable_fire_control`)는 꺼진 상태로 측정했다.

## 0. 해결 — 포탑이 명령을 따르지 않던 문제 (원인 규명 및 우회 적용)

지난 세션에서 "전체 장면으로 띄우면 포탑이 명령을 전혀 따르지 않는다"로 남겨 둔 항목이다.
결론부터 적으면, **전체 장면과 무관한 포탑 자체의 문제**였고 우회 수정을 적용해 실측으로
동작을 확인했다.

### 0.1 확정된 조건

pan 명령이 pan 관절의 현재 위치와 **정확히 같으면**(둘 다 0.0 인 기동 직후가 대표적)
tilt 관절이 명령을 전혀 따르지 않는다. pan 자체는 언제나 정상 동작한다.

`ciws_turret` 단독(`view.launch.py`)에서도 그대로 재현된다. FCS 도 표적 드론도 필요 없다.

| 명령 [pan, tilt] | pan 오차 | 결과 |
|---|---|---|
| [0.00, 0.38] 8초 | 0 | 두 관절 모두 무반응 |
| [0.00, 0.58] 8초 | 0 | 두 관절 모두 무반응 |
| [0.30, 0.28] | 0.30 | 즉시 두 관절 모두 정상 |
| [0.00, 0.38] (pan 이 0.3 에 있을 때) | -0.30 | 정상 |

지난 세션에서 "단독 실행은 정상"으로 판단했던 것은 그때 쓴 시험 명령이 [0.2, 0.5] 로
pan 이 0 이 아니었기 때문이다. 즉 단독 실행도 사실은 같은 결함을 갖고 있었다.

### 0.2 성질

- **컨트롤러 목록 순서가 아니라 pan 관절 자체가 조건이다.** `controllers.yaml` 의 joints 를
  [tilt, pan] 으로 뒤집고 첫 명령 [0.0, 0.38](= tilt 0.0 / pan 0.38)을 주면 즉시 정상
  동작했다. 막히는 쪽은 언제나 "pan 오차가 0" 인 경우다.
- **일회성 잠금 해제가 아니라 동시 조건이다.** 컨트롤러 활성화 직후 pan 을 0.05 rad 로
  슬루시켰다 되돌려도(실제로 관절이 0.012 -> 0.025 로 움직인 것을 확인) 그 뒤 pan 오차가
  다시 0 이 되면 tilt 는 그대로 얼어붙는다.
- 증상이 조용하다. 토픽에는 명령이 20~30 Hz 로 정상적으로 흐르고, 컨트롤러는 active,
  command interface 도 claimed 이며 런치 로그에 오류가 하나도 없다.

### 0.3 기각된 원인 (재조사 금지)

FCS 노드 / 표적 스폰 / 전체 장면 구성, CPU 부하, DDS 매칭 및 QoS(발행자와 컨트롤러
구독은 처음부터 정상 연결되어 있었다 — 발행자의 `get_subscription_count()` 가 기동
시점부터 1 이었다), `position_proportional_gain`, 컨트롤러 joints 순서, pan 의
continuous/revolute 관절 종류, tilt `command_interface` 의 min/max, URDF 의
`initial_value`(컨트롤러 활성화 이전에 소진되어 효과 없음), 컨트롤러 활성화 직후의
일회성 슬루.

지난 세션에서 기각해 둔 항목(TF 콜백 경쟁, 동적 TF 발행 중단)도 그대로 유효하다.
`TransformListener(spin_thread=True)` 를 쓰지 말라는 경고도 그대로다.

### 0.4 적용한 수정

근본 원인은 gz_ros2_control / DART 상류 동작으로 보이며 거기까지는 규명하지 못했다.
그래서 **pan 오차가 0 이 되는 상태 자체를 만들지 않는 것**으로 우회했다.
`smash_fcs_node.py` 의 `_publish_command` 에서 pan 명령에 매 발행마다 부호가 뒤집히는
아주 작은 흔들림(`PAN_DITHER_RAD = 5e-4` rad)을 얹는다.

진폭 근거: 카메라 화각 0.4 rad / 640 px = 6.25e-4 rad/px 이므로 5e-4 rad 은 약 0.8픽셀,
즉 1픽셀 미만이다. 정렬 허용오차 `_align_tolerance_px` 가 35 픽셀이므로 조준·격발 판정에
영향이 없다. 실측에서도 관절 위치 흔들림은 ±0.0004 rad(약 0.6픽셀)에 머물렀다.

**진폭을 줄이려면 반드시 다시 실측할 것.** 임계값 아래로 내려가면 아무 오류 없이 조용히
재발한다.

전체 장면(`smash_scene.launch.py`, 헤드리스, 외부 발행자 없음)에서 수동 슬루로 확인했다.

| 시각 | 명령 tilt | 관절 tilt |
|---|---|---|
| t=8s | 0.38 (슬루 프리셋) | 0.0679 -> 0.3798 -> 0.3800 |
| t=23s | 0.58 | 0.5551 -> 0.5800 |

수정 전 같은 절차에서는 tilt 가 75초 동안 0.0000 에서 전혀 움직이지 않았다.

### 0.6 남은 일

- 상류(gz_ros2_control) 근본 원인 규명은 미완이다. 우회이지 수정이 아니다.
- 이 우회는 FCS 노드 안에 있으므로, `view.launch.py` 만 띄우고 `ros2 topic pub` 로 직접
  조종할 때는 여전히 pan 을 0 이 아닌 값으로 한 번 지시해야 tilt 가 움직인다.
- 포탑이 움직이게 됐으므로 이제 원래 목표인 탐지 -> 조준점 -> 격발 통합 검증을 진행할 수
  있다. 아직 하지 않았다.

## 9. 스코프 뷰어 버퍼링 수정 (별개 문제, 해결)

렌더러를 GPU 로 바꾼 뒤에도 "버퍼링이 심하고 반응이 느리다"는 증상이 남아 있었다. 조사
결과 이는 시뮬레이터 속도와 무관한, 영상 전송 경로의 독립된 결함이었다.

원인은 세 가지였다.

1. **뷰어가 밀린 프레임을 버리지 않았다.** `scripts/win_scope_viewer.py` 가 메인 루프에서
   4096바이트씩 읽으면서 매 반복 `cv2.waitKeyEx(1)` 을 호출했다. waitKey 한 번이 최소
   1~5 ms 를 쓰므로 읽기 속도가 초당 1 MB 안팎으로 묶이는데, 서버는 그보다 빠르게
   프레임을 밀어낸다. 소비가 생산을 못 따라가면 TCP 버퍼에 프레임이 쌓여 화면 지연이
   시간이 갈수록 누적된다. 오래 켜둘수록 심해지는 것이 이 결함의 특징이다.
2. **서버가 같은 화면을 초당 30회 JPEG 로 압축했다.** 실제 영상은 초당 10장 남짓이다.
3. **서버 렌더 루프가 초당 약 100회 돌며** 640x640 화면을 매번 새로 복사·렌더링했다.

수정 내용은 다음과 같다.

| 파일 | 수정 |
|---|---|
| `scripts/win_scope_viewer.py` | 수신을 전용 스레드로 분리하고, 버퍼에 밀린 프레임은 버린 뒤 항상 최신 한 장만 표시 |
| `drone_sim/drone_sim/smash_scope_viewer.py` | 새 영상이 왔을 때만 렌더링, 새로 렌더링된 프레임일 때만 JPEG 압축, 스트림 대기 0.033 초 -> 0.005 초 |

수정 후 측정(격발 제어 켜고 5번과 동일 조건)에서 스트림 수신은 5.7 fps 로 FCS 생산량과
일치했고, 프레임 간격은 중앙값 178 ms / 최대 440 ms 로 일정하게 유지되었다. 즉 지연 누적은
사라졌다. 스코프 뷰어 프로세스는 CPU 상위 목록에서 사라졌다.

다만 이는 "지연 누적"을 없앤 것이지 초당 프레임 수를 늘린 것은 아니다. 프레임 수 자체는
아래 10절의 제약을 받는다.

## 10. 센서 주기 15 Hz 실험 (되돌림) 및 하드웨어 한계

카메라·레이저 `update_rate` 를 30 에서 15 로 낮춰 2회 반복 측정했다.

| 조건 | 카메라 | FCS 처리율 |
|---|---|---|
| 30 Hz (기존) | 평균 9.9 Hz | 평균 5.0 Hz |
| 15 Hz | 평균 6.6 Hz | 평균 5.1 Hz |

화면에 보이는 FCS 처리율은 사실상 변화가 없고 카메라 주기만 떨어졌다. 얻는 것이 없으므로
30 Hz 로 되돌렸고, 재실험을 막기 위해 URDF 주석에 측정 결과를 남겼다.

또한 `.wslconfig` 로 CPU 코어를 늘리는 방안은 **불가능**하다. 호스트 CPU 가 Intel i5-7400
으로 물리 4코어이며 하이퍼스레딩이 없어, WSL2 가 이미 전체 4코어를 사용하고 있다. 메모리는
호스트 32 GB 중 WSL 에 약 15 GB 가 할당되어 있으며 병목이 아니다.

결론적으로 이 PC 에서 측정으로 확인된 개선 수단은 다음 두 가지뿐이다.

1. CPU 렌더링 -> GPU 렌더링 전환 (적용 완료, FCS 처리율 약 2.7배)
2. 카메라 해상도 640 -> 320 (미적용, FCS 처리율 약 3배, 탐지 정확도와 READY 판정 기준
   저하를 동반하므로 5절의 조건을 함께 처리해야 함)

## 11. 탐지 -> 조준점 -> 격발 통합 검증 (2026-09-12 후속)

0절에서 포탑이 움직이게 된 뒤 실제로 통합 검증을 돌렸다. 전부 헤드리스, 정지 호버링
단일 표적, `enable_fire_control:=true fire_mode:=auto` 조건이다.

### 11.1 먼저 고친 것 — 실측 위치 토픽이 비어 있었다

`drone_sim/models/drone/model.sdf` 의 PosePublisher 가 `static_publisher` 를 true 로
두고 있었다. 이 설정에서 gz-sim 은 **변하지 않는 자세**를 본 토픽이 아니라
`<이름>/pose_static` 으로 따로 내보낸다. 1단계 표적은 정지 호버링이라 자세가 변하지
않으므로 `/model/drone/pose` 에는 발행자만 있고 데이터가 한 건도 흐르지 않았다.

| 토픽 | static_publisher=true (수정 전) | false (수정 후) |
|---|---|---|
| `/model/drone/pose` | 3초간 **0건** | 3초간 144줄 |
| `/model/drone/pose_static` | 3초간 136줄 | 발행자 없음 |

그 결과 첫 시도에서 **741발 전부가 UNVERIFIED** 였다. 격발은 정상이므로 증상이 조용하다.
`static_publisher` 를 false 로 바꾸고 `update_frequency` 30 을 주었다. 이렇게 두면 정지
표적이든 이동 표적이든 항상 같은 토픽으로 나오므로 4단계(회피 기동)까지 하나로 처리된다.
토픽 이름 `/model/drone/pose` 자체는 실측으로 맞음을 확인했다(gz.msgs.Pose,
frame_id `turret_world`, child_frame_id `drone`). 문서에 "가정"으로 남아 있던 항목을
이것으로 해소한다.

### 11.2 검증 절차상 알아 둘 것 — 포탑은 표적을 자동 추종하지 않는다

`smash_fcs_node.py` 는 `self._pan_goal = self._user_pan` 으로 사수가 지시한 각도만
유지한다. 설계 의도대로다(SMASH 는 서보 무기가 아니라 자문 조준경이다). 따라서
READY(정렬 오차 <= 35 px)는 사수가 직접 조준선을 리드 레티클에 맞춰야 도달하며,
무인 검증을 하려면 사수 조작을 대신할 것이 필요하다. 상태 문자열에는 오차의 크기만
있고 방향이 없으므로, 세 점 측정(기준 + pan 탐침 + tilt 탐침)으로 오차 벡터를 복원해
되먹임하는 방식으로 자동 조준했다. 첫 반복에서 바로 READY 에 도달했다.

### 11.3 결과 — 근거리 10.8 m

표적 (10.0, 0, 4.2), 경사거리 약 10.8 m.

| 항목 | 값 |
|---|---|
| 상태 전이 | SEARCH -> ALIGN(19px) -> READY |
| FCS 처리율 | 평균 10.1 fps |
| 격발 | 741 발 (예측 비행시간 11.3 ms 일정) |
| 판정 | HIT 1 / MISS 355 / UNVERIFIED 385 |
| 명중률 | 0.3 % |
| 빗나간 거리 | 최소 0.233 / 중앙 0.282 / 최대 0.291 m |

전 과정(탐지 -> 추적 -> 거리 -> 조준해 -> 정렬 -> 격발 -> 판정)이 끊김 없이 도는 것은
확인했다. 그러나 **빗나간 거리가 0.233~0.291 m 에 거의 고정**되어 있다. 산포가 아니라
계통 편향이며, 명중 반경 0.235 m(= `target_characteristic_size_m`/2)를 조금씩 벗어나
명중률이 0.3 % 로 주저앉는다. 10.8 m 에서 0.28 m 는 약 26 mrad(1.5도)에 해당한다.

### 11.4 결과 — 로드맵 1단계 조건 35 m

표적 (33.0, 0, 12.5), 경사거리 약 35.3 m.

**상태가 SEARCH 를 한 번도 벗어나지 못했다. 격발 0 발.** 조준이 빗나가서가 아니다.
캡처한 프레임을 보면 표적이 화면 중앙에 또렷하게(가로 약 20 px) 들어와 있고 HUD 의
십자선이 표적 위에 얹혀 있는데도 `STATE SEARCH`, `RNG --.--m [---]` 이다. 즉
프레이밍·지향은 정확하고 **탐지기가 이 크기의 표적을 잡지 못하는 것**이다.

로드맵 1단계 기준 조건이 바로 이 35 m 정지 호버링이므로, 현 상태로는 1단계 통과를
주장할 수 없다.

### 11.5 함께 드러난 설계상의 문제 — READY 기준의 단위

READY 판정은 화소 단위(`_align_tolerance_px` = 35 px = 21.9 mrad)인데 명중 판정은
미터 단위(반경 0.235 m)다. 두 기준이 일치하는 거리는 한 점뿐이다.

| 거리 | 35 px 이 대응하는 거리오차 | 명중 반경 | 관계 |
|---|---|---|---|
| 10.8 m | 0.236 m | 0.235 m | 거의 일치 (우연) |
| 35 m | 0.77 m | 0.235 m | READY 가 3.3배 헐겁다 |

즉 거리가 멀어질수록 READY 는 명중을 전혀 보장하지 못하는 표시가 된다. 5절에서 지적한
"해상도를 낮추면 READY 기준이 소리 없이 완화된다"와 같은 뿌리의 문제이며, 정렬 허용오차를
각도가 아니라 표적 거리 기반의 미터 기준으로 환산해야 한다.

### 11.6 남은 일 (우선순위 순)

1. **35 m 탐지 실패.** 로드맵 1단계 기준 조건이므로 최우선이다. 표적이 화면에 또렷이
   보이는데도 못 잡으므로 가중치·`conf_thres`·입력 해상도(`imgsz`) 쪽을 봐야 한다.
   5절에 적힌 대로 YOLO 호출이 `imgsz` 를 넘기지 않아 기본값 640 으로 레터박스되는
   점도 함께 확인할 것.
2. **0.28 m 계통 편향.** 근거리에서 전 과정이 도는데도 명중률이 0.3 % 인 직접 원인이다.
   거의 일정한 값이므로 각도 편향이 아니라 고정 기하 오프셋일 가능성이 있다
   (`gun_to_camera_optical_m` = [0.159, 0.21, 0.25], `scope_to_muzzle_m` 의 부호·중복
   적용 여부). 35 m 에서 격발이 되면 편향이 거리에 비례하는지 일정한지로 두 가설을
   가를 수 있다.
3. **판정 52 % 가 UNVERIFIED.** 실측 위치 토픽을 고친 뒤에도 절반이 남는다. 30 Hz 로
   발행되고 `ground_truth_timeout_s` 가 0.5 초이므로 정상이라면 거의 다 판정되어야 한다.
   4코어 포화 상태에서 브리지·콜백이 밀리는 것으로 보이며, 명중률 통계의 표본을 절반으로
   깎으므로 정량 보고 전에 해소해야 한다.
4. **명중 반경 0.235 m 가 실측값이 아니다.** `target_hit_radius_m` 이 -1 이라
   `target_characteristic_size_m`(0.47, 이 값 자체도 추정치)의 절반으로 유도된다.
   명중률을 보고하려면 실제 동체 크기로 보정해야 한다.

### 12.2 (1) 35 m 탐지 실패 — 입력 해상도 문제였다

임계값도 가중치도 아니었다. 캡처한 35 m 프레임으로 오프라인 스윕한 결과:

| imgsz | 최고 신뢰도 | 전체프레임 추론시간 |
|---|---|---|
| 640 (기존) | **0.020** | 32.5 ms |
| 960 | 0.585 | 55.1 ms |
| 1280 | 0.701 | 93.3 ms |
| 1920 | 0.720 | - |

표적이 640 프레임에서 24x10 px 라 stride-32 격자에 해상되지 않는다. `conf_thres` 를
0.02 까지 낮추면 "잡히기"는 하지만 잡음 수준이라 오탐이 쏟아지므로 해법이 아니다.

Ultralytics 는 입력을 imgsz 로 레터박스하므로 **ROI 경로는 작은 crop 이 640 으로 확대되어
이미 고해상도 효과를 얻고 있었다.** 문제는 전체 프레임 경로뿐이다. 그래서
`bridge/optical_flow_tracker.py` 의 전체 프레임 호출에만 `imgsz` 를 넘기도록 고쳤다
(`OpticalFlowTracker(acquire_imgsz=960)`). 비용은 표적을 포착하기 전에만 든다.

### 12.3 (2) 0.28 m 계통 편향 — 카메라가 포신 중심선에서 0.21 m 옆에 있었다

빗나감을 크기가 아니라 **벡터**로 보니 즉시 드러났다.

| 성분 | 10.8 m | 35.3 m | 표준편차 |
|---|---|---|---|
| X | -0.181 | +0.530 | 0.004 / 0.812 |
| **Y** | **+0.210** | **+0.210** | **0.002 / 0.007** |
| Z | +0.048 | +0.294 | 0.001 / 0.289 |

Y 가 거리와 무관하게 정확히 +0.210 m 로 고정이고, 이는 `gun_to_camera_optical_m[1]`
과 같은 값이다. 기구학은 단순하다. 가상 탄환은 카메라에서 유도한 총구(world y = +0.21)
에서 출발하는데 발사 방향은 포신 보어사이트이고, pan 이 0 이면 좌우 성분이 0 이다.
표적이 y = 0 에 있으면 **수학적으로 도달할 수 없고** 정확히 0.21 m 빗나간다. 두 런 모두
pan 이 0.000 에 머물러 있었던 것이 직접 증거다.

보정에 필요한 pan 각은 10.8 m 에서 31 px, 35 m 에서 9.5 px 로 **둘 다 READY 임계
35 px 안**이다. 그래서 "정렬 완료" 상태로 계속 빗나가는 조용한 실패였다.

`smash_fcs.yaml` 의 `scope_to_muzzle_m: [0.45, 0.0, -0.066]` 은 "조준경이 총열 바로 위에
정렬(좌우 0)"을 전제하는데 URDF 가 그 전제를 깨고 있었다. URDF 의 광학중심과 레이저를
gun_link 중심선(좌우 0)으로 옮기고 `gun_to_camera_optical_m` 을 [0.159, 0.0, 0.25] 로
맞췄다. 결과: Y 편향 +0.210 -> **-0.000 m**, 10.8 m 명중 1발 -> 313발.

### 12.4 (3) UNVERIFIED 52 % — 오래되어서가 아니라 부호 때문에 버려지고 있었다

`fire_control.py` 는 `gt_age = now - ground_truth_timestamp` 가 음수면 판정을 버렸다.
그런데 실측해 보니 타임아웃(0.5초) 초과는 **0 건**이고, `gt_age` 는 0 근처에서 진동하며
음수 비율이 24.2 % 였다(부하 없는 관찰자 기준, 범위 -0.011 ~ +0.009초).
FCS 본체에서는 더 벌어져 **-0.051 ~ -0.106초**까지 갔다.

원인은 `/clock` 이 640x640 영상 및 1089빔 PointCloud2 와 **같은 parameter_bridge
프로세스**에 묶여 있어 시각 갱신이 대용량 메시지 뒤에 줄을 선 것이다. 그러면 노드의
sim 시계가 실측 스탬프보다 뒤처져 더 신선한 값이 "미래 데이터"로 버려진다.

두 가지를 함께 고쳤다.

1. `view.launch.py` 에서 `/clock` 을 전용 브리지 프로세스로 분리했다.
2. `fire_control.py` 의 검사를 `abs(gt_age) > timeout` 으로 대칭화했다. 과거 쪽 0.5초를
   이미 허용하면서 미래 쪽만 0 으로 막을 근거가 없다.

결과: UNVERIFIED 52 % -> 20.5 % -> **0 %**.

### 12.5 (4) 명중 반경 — 용도가 다른 두 상수를 분리했다

`target_hit_radius_m` 이 -1 이라 `target_characteristic_size_m`/2 로 자동 유도되고
있었다. 두 상수는 용도가 다르다.

- `target_characteristic_size_m` : 카메라가 **보는** 폭. 거리 역추정(R = f*S/s)용.
- `target_hit_radius_m` : 탄이 **맞는** 동체. 명중 판정용.

묶어 두면 보이는 크기가 커질수록 명중 판정도 함께 느슨해져 명중률이 부풀려진다.

`drone_sim/meshes/drone.stl` 경계상자를 직접 재니 0.3542 x 0.3542 x 0.0921 m,
`model.sdf` 의 충돌 상자는 0.35 x 0.35 x 0.10 m 였다. 충돌 상자의 평면 단면과 같은
넓이를 갖는 원의 반지름 0.35/sqrt(pi) = **0.1975 m** 를 명중 반경으로 명시했다.

**주의 — 메시 치수를 특성 크기에 그대로 넣으면 안 된다.** 메시 대각 투영폭 0.5009 를
`target_characteristic_size_m` 에 넣어 봤더니 35 m 사거리 추정이 약 2.1 m 길어져
계통 빗나감이 0.82 m -> 3.21 m 로 악화되고 명중이 0 발이 되었다. 바운딩박스는 대각선이
아니라 실루엣의 축정렬 폭을 재며 그 값은 표적 자세와 탐지기 성향에 좌우된다. 그래서
이 파일이 원래 적어 둔 절차대로 실측 보정했다.

    S_correct = 0.47 * 35.03 / (35.03 + 0.813) = 0.459

결과: 35 m 계통 편향 0.819 -> **0.205 m**, 계통 비율 100 % -> 30 %.

   35 m 에서 바운딩박스가 24 px 뿐이라 1 px 오차가 곧 4 %(약 1.4 m) 사거리 오차가 된다.
   레이저 거리측정기가 있는데 이 거리에서 채택되지 않고 있는 것으로 보인다 —
   `laser_cross_check_sigma` 게이트가 바운딩박스 추정치와 비교해 기각하는지 확인할 것.
   35 m 명중률(9.9 %)을 올리려면 이것이 핵심이다.
2. **판정 시점의 정의.** 현재는 예측 비행시간이 지난 시각의 탄 위치와 표적을 비교한다.
   사거리 추정이 빗나가면 탄이 표적을 스쳐 지나가는데도 평가 시점이 어긋나 MISS 로
   기록될 수 있다. 궤적과 표적의 **최근접 거리**로 바꾸는 편이 물리적으로 맞다.
3. **READY 기준의 단위** (11.5절). 화소 기준이라 거리가 멀수록 명중을 보장하지 못한다.

4. **`target_characteristic_size_m` 는 이 표적·이 가중치 기준 보정값이다.** 표적 모델이나
   탐지기를 바꾸면 같은 절차로 다시 보정해야 한다.
5. **`acquire_imgsz` 960 은 탐색 중 프레임당 +22.6 ms 를 쓴다.** 4코어 환경에서 탐색
   구간 처리율이 떨어지므로, 표적 포착이 느리다고 느껴지면 이 값과 맞바꾼 것임을
   기억할 것.

### 13.3 (2) 명중 판정을 최근접 거리로 바꿨다

이전에는 "예측 비행시간이 지난 순간의 탄 위치"와 표적을 비교했다. 그러면 사거리
추정이 빗나갔을 때 탄이 표적을 스쳐 지나가는데도 평가 시점이 어긋나 MISS 가 된다.
실제로 35 m 에서 사거리 산포(표준편차 0.75 m)가 그대로 빗나감 거리에 실렸다.

명중은 "탄이 표적 부피를 통과했는가"이지 "정해진 시각에 표적 옆에 있었는가"가
아니므로, 궤적과 표적의 **최근접 거리**로 판정하도록 바꿨다
(`FireController.closest_approach`). 궤적을 국소 직선으로 근사하는데, 880 m/s 탄의
40 ms 비행 중 중력 낙하가 8 mm 뿐이라 최근접점 부근에서는 사실상 직선이다.

사거리 추정 오차가 사라진 것은 아니므로, 진단용으로 `along_track_error_m`(탄도
방향으로 표적이 얼마나 앞/뒤였는지)을 판정 payload 에 함께 싣는다.

### 13.4 (3) READY 허용오차를 거리 기반으로 바꿨다

`_align_tolerance_px` 가 35 픽셀 고정이었다. READY 는 "이대로 쏘면 맞는다"를 뜻해야
하는데, 맞는지는 미터 단위 명중 반경으로 정해진다. 화소는 각도 단위이므로 두 기준이
일치하는 거리는 한 점뿐이다.

| 거리 | 35 px 이 대응하는 거리오차 | 명중 반경 0.1975 m 에 필요한 화소 |
|---|---|---|
| 10.8 m | 0.236 m | 28.9 px |
| 35.0 m | 0.766 m | 8.8 px (기존 기준이 4배 헐거웠다) |

허용오차를 `fx * hit_radius / R` 로 유도하도록 바꿨다(`align_tolerance_max_px` 35,
`align_tolerance_min_px` 3 으로 상·하한). 명중 반경은 격발 판정과 정렬 판정이 같은
값을 쓰도록 한 곳(`_hit_radius_m`)에서 정한다.

부작용: 35 m 에서 READY 가 훨씬 엄해졌다. 검증용 자동 사수의 수렴 목표도 25 px 에서
5 px 로 조여야 READY 에 도달한다. 실제 사수에게도 그만큼 정밀한 조준을 요구한다는
뜻이며, 이것이 물리적으로 정직한 기준이다.

## 14. 기동 시 컨트롤러 활성화 실패 (2026-09-13, 사용자 실행 중 발견)

사용자가 런처 5번(수동 격발 + 스코프 뷰어)으로 실행했더니 방아쇠를 당겨도
`SHOTS` 가 0 에서 늘지 않았다. 뷰어 로그에는 `[BANG!] 사수 격발 명령 전송` 이
정상적으로 찍혔다.

### 14.1 원인

HUD 가 `STATE TRACK(NO TF)` 를 표시하고 있었고, 실행 중인 세션을 조회하니
컨트롤러 하나가 올라오지 않았다.

    turret_controller        active
    joint_state_broadcaster  unconfigured   <- 활성화 실패

`/joint_states` 와 `/tf` 둘 다 비어 있었다. 연쇄는 다음과 같다.

    joint_state_broadcaster 실패
      -> /joint_states 중단
      -> robot_state_publisher 가 동적 TF(turret_link, gun_link) 발행 중단
      -> FCS 의 base_footprint <- camera_link_optical 조회 실패
      -> 상태가 TRACK(NO TF) 에 갇힘 -> 조준해(리드 레티클) 생성 안 됨
      -> 격발 거부 (조준각 없이 가상 탄환을 만들지 않는 것이 설계다)

포탑은 움직이고 탐지도 되고 레이저도 정상(`RNG 10.39m +-0.02 [LSR]`)이라
겉보기에는 멀쩡해 보이는 것이 이 고장의 특징이다.

이 실패 모드 자체는 지난 세션이 `view.launch.py` 주석에 이미 적어 두었고 스포너
제한시간을 60초로 늘려 두었는데, 그것만으로는 부족했다.

### 14.2 구조적 문제

기존 구성은 2단 사슬이었다.

    OnProcessExit(spawn) -> jsb 스포너
    OnProcessExit(jsb)   -> turret 스포너

`OnProcessExit` 는 성공/실패를 가리지 않으므로 **jsb 가 실패해도 turret 은 그대로
올라간다.** 그래서 "반쪽만 살아난 채 조용히 망가진" 상태가 만들어진다.

### 14.3 수정

두 컨트롤러를 한 번의 spawner 호출로 묶고, 모델 스폰 직후 3초 여유를 두었다.

- `switch_controller` 서비스 왕복이 2회 -> 1회로 줄어 CPU 포화 시 경쟁 확률이 낮아진다.
- 실패할 때는 둘 다 실패하므로 로그에 분명히 드러난다.
- 모델 스폰 직후는 Gazebo 가 메시·센서를 올리느라 가장 바쁜 구간이라 그 순간을 피한다.

### 14.4 검증

배치파일 5번과 같은 조건(전체 장면 + 격발 제어)으로 **10회 반복**했다.

| 확인 항목 | 결과 |
|---|---|
| 두 컨트롤러 모두 active | 10 / 10 |
| `/joint_states` 수신 | 10 / 10 (54~78 Hz) |
| TF `base_footprint <- camera_link_optical` | 10 / 10 정상 |
| 스포너 경고·오류 로그 | **0 건** |

수정 전 로그에는 `Failed getting a result from calling /controller_manager/switch_controller`,
`Aborting, no controller is switched! (::STRICT switch)`,
`spawner ... process has died, exit code 1` 이 반복적으로 나타났다. 수정 후에는 10회
전부에서 한 건도 나오지 않았고 매번 `Configured and activated` 가 두 컨트롤러 모두에
대해 찍혔다.

간헐적 고장이므로 10회 무결이 완전한 증명은 아니다. 다만 경고 자체가 사라진 것은
단순히 운이 좋았던 것과는 구분되는 근거다.

### 14.5 그래도 재발하면

시뮬레이터를 내릴 필요 없이 아래로 되살릴 수 있다(실제로 이 방법으로 사용자의
실행 중 세션을 복구했다 — `/joint_states` 가 약 55 Hz 로 돌아왔다).

    ros2 run controller_manager spawner joint_state_broadcaster         -c /controller_manager --controller-manager-timeout 60 --switch-timeout 60
