Design Philosophy

자동 발사 시스템이 아닙니다. 이 엔진은 조준만 보조하며, 최종 발사는 항상 사용자가 직접 수행합니다.

파이프라인 상 위치

Camera → YOLO11s-GA → SmartTracker 까지는 기존 완성분이며 수정하지 않았다. Aiming Engine은 HUD에 표시할 조준 정보만 계산하고, 발사 여부의 최종 판단과 실행은 사람(운용자)이 담당한다.

핵심 설계 결정 — 물리 엔진 (v1부터 유지)

  1. 01

    LeadPrediction과 HitEquation의 역할 분리

    TargetState.predict(t)를 유일한 예측 소스로 두고, LeadPrediction은 솔버의 초기 추정값만 생성한다.

  2. 02

    명중 방정식을 3원 연립으로 정의

    x = [비행시간 t, 방위각, 고각] 3개 미지수 · 3개 방정식(x,y,z)을 동시에 푼다. 여기서 "탄도"는 실제 발사체가 아니라 HUD 조준선을 계산하기 위한 시뮬레이션이다.

  3. 03

    NewtonSolver는 탄도학을 모른다

    equation.residual(x)만 호출하고 자코비안은 유한차분으로 근사. 드래그·바람·G1/G7이 추가되어도 솔버 코드는 변경 없음.

  4. 04

    ProjectileModel = RK4 + 플러그형 ForceModel 리스트

    v1은 forces: [gravity]뿐. 중력만 있을 때 RK4는 스텝 크기와 무관하게 정확하다.

  5. 05

    물리 연산은 전부 World frame, Scope frame은 마지막 변환에만

    TargetState / LeadPrediction / HitEquation / ProjectileModel은 관성 좌표계(World)에서만 동작. AimSolver 마지막 단계에서만 world_to_scope_direction으로 변환해 HUD용 방위각·고각을 뽑는다.

  6. 06

    이전 프레임 해로 워밍스타트

    목표가 매끄럽게 움직이면 AimSolver가 직전 프레임의 수렴 해를 다음 프레임 초기값으로 재사용 — 콜드 솔브 대비 반복 횟수 감소.

구현 중 발견 · 수정한 버그

① 좌표계 축 관례 혼동 (v1)

카메라(Z-forward, 핀홀)와 조준경(X-forward, FLU) 축 관례를 혼동. camera_to_scope()가 마운트 보정 회전만 적용하고 고정 축 재배열이 누락됨.

수정 전
azimuth = 180°, elevation = ~90° → 조준선이 뒤집혀 하늘을 가리킴
수정 후
azimuth = 0°, elevation = 0.09° → 245m·850m/s 기준 타당한 낙차 보정

수정: _CAMERA_TO_SCOPE_AXES 고정 변환 행렬 추가 + 회귀 테스트로 축 매핑 고정.

② aim_ready가 SEARCH 상태에서도 True로 뜨는 문제 (이번 리브랜딩)

AimReadinessLogic은 그 프레임만 보고 독립적으로 판단하기 때문에, 상태 머신이 아직 SEARCH인 첫 프레임에도 거리·오차 조건만 맞으면 aim_ready = True가 나올 수 있었다 — HUD가 트래킹이 채 안정되기도 전에 "조준 완료" 신호를 켜는 셈.

수정 전
state = SEARCH aim_ready = True (!!)
수정 후
aim_ready = (state == READY) and AimReadinessLogic.evaluate(...)

수정: aiming_manager.py에서 상태 머신 결과가 나온 뒤에 aim_ready를 계산하도록 순서 변경, READY 상태를 필수 조건으로 게이팅. 통합 테스트로 "aim_ready는 AIM/READY 상태에서만 True"를 고정.

v3 실시간 최적화 — 45 fps 대응

SmartTracker까지 45fps(프레임당 예산 22.2ms) 달성 후, Aiming Engine의 spike 17.1ms가 전체 파이프라인 병목으로 확인됨. 알고리즘·인터페이스는 전혀 변경하지 않고 연산 비용만 절감했다.

① projectile_model.py — 중력 해석해 단락 (효과 최대)

forces: [gravity] 일 때 RK4(O(n_steps × 4 derivative 호출))를 해석해 p(t) = p₀ + v₀t + ½g t²로 대체 — 수학적으로 동일한 결과, O(1) 비용. 비선형 force(drag, wind …) 추가 시 자동으로 RK4 경로로 fallback되어 plug-in 구조 유지.

수정 전
n_steps * 4 derivative 호출 → Newton iter 당 ~수십 번의 연산
수정 후
p = p0 + v0*t + 0.5*g*t² (3줄) → Newton iter 당 O(1) 벡터 연산

② aim_solver.py — warm_start fallback 수정

기존에는 Newton 미수렴 시 self._previous_solution = None으로 버려 다음 프레임이 cold solve가 됐다. 수정 후 미수렴이어도 best-effort 해를 보존해 다음 프레임 warm_start에 활용 — cold solve 연쇄 방지.

수정 전
self._previous_solution = result.x.copy() if result.converged else None
수정 후
self._previous_solution = result.x.copy() # 항상 보존

③ target_state.py — polyfit 3회 루프 → lstsq 벡터화

ConstantVelocityEstimator의 속도 추정이 axis별 np.polyfit 3회 호출 → np.linalg.lstsq 1회로 x/y/z를 동시에 처리. 결과는 수학적으로 동일.

수정 전
velocity = np.array([ np.polyfit(ts, ps[:, ax], 1)[0] for ax in range(3)])
수정 후
A = np.column_stack([ts, ones]) coeffs, *_ = np.linalg.lstsq(A, ps) velocity = coeffs[0] # (3,)

④ config/aiming_engine.yaml — max_iterations 20 → 5

해석해 적용 후 warm-start 솔브는 1~2회 만에 수렴. 급기동 시 spike를 하드 캡으로 억제. 미수렴 해는 ②의 fallback이 다음 프레임에 재활용하므로 정확도 영향 최소.

범위 밖

영구 제외 — 설계 철학

자동 발사 기능. 나중에 "추가"할 계획이 아니라, 이 시스템의 정의상 존재하지 않는다. AimStateMachine에는 발사 상태가 없고, FireCommand에 대응하는 클래스도 없다. 최종 발사는 항상 사람이 수행한다.

보류 탄도 물리 확장

  • 공기저항(Drag) · 바람(Wind)
  • 탄도계수 G1 / G7

추가 방법: ForceModel 서브클래스 → FORCE_REGISTRY 등록 → YAML forces 리스트에 이름 추가. 기존 모듈 수정 불필요.

보류 목표 추정 고도화

  • 등가속도 추정기
  • 칼만 필터

추가 방법: MotionEstimator 서브클래스 → build_estimator() 등록 → YAML target_state.estimator 변경.

참고 HUD 렌더링

  • 실제 화면 오버레이 렌더링
  • Jetson 상 실물 디스플레이 연동
